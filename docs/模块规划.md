> 最后更新：2026-07-28  
> 配套文档：[nebula-current-state-analysis.md](./nebula-current-state-analysis.md)（完成度与缺口）、[nebula-development-detailed-plan.md](./nebula-development-detailed-plan.md)（专项工程计划）、`nebula/docs/development-plan.md`（波次与关口）

## 1. 项目定位

Nebula 是一个基于 Spring Boot 的企业级应用运行平台。

目标不是重新实现 Spring Framework，而是在 Spring Boot 基础上提供企业应用所需的平台能力：

- 应用运行环境
- 动态插件体系
- 资源治理体系
- 版本管理体系
- 发布部署体系
- 统一配置加载与刷新（basic / center 双模式）
- 任务调度体系
- 接口集成平台
- 安全认证体系
- 多租户体系

Nebula 的最终目标：

> 形成统一的企业应用运行平台，使业务应用、接口集成、任务调度、插件扩展均基于统一的平台模型运行。

# 3. 核心平台模型

Nebula 平台核心由以下部分组成：

```text
                 Resource

                    |

              Governance

                    |

              Version Control

                    |

                Release

                    |

                Runtime

                    |

        Plugin / Camel / Task / App
```

---

## 3.1 Resource

资源模型。

定义：

> 平台中所有可管理对象。

包括：

- Camel Route
- Plugin
- Task
- Config
- DataSource
- API
- Application

统一资源模型：

- 资源标识、类型、归属
- 租户、版本、状态

---

## 3.2 Governance

资源治理。

负责：

- 创建申请
- 修改申请
- 发布申请
- 审核流程
- 操作审计

---

## 3.3 Version Control

版本管理。

负责：

- 快照
- 差异比较
- 历史版本
- 回滚

不负责领域差异。

例如：

Camel Route 如何比较由 Camel 自己实现。

---

## 3.4 Release

发布管理。

负责：

- 发布流程
- 发布状态
- 部署动作
- 回滚

---

## 3.5 Runtime

运行时环境。

负责：

- 生命周期
- 上下文
- 事件
- 扩展加载

---

# 4. nebula-tools

## 定位

纯工具库，仅依赖 JDK / SLF4J 等最小基础库。

提供无状态工具方法；**不包含** Spring 集成、运行时上下文或领域模型。

---

## 结构

单一 Maven 模块，按包组织工具类（字符串、时间、Servlet、对象、BPMN 解析等），**不拆分子模块**。

```text
nebula-tools/    # 单模块 artifact
```

# 5. nebula-runtime

## 定位

Nebula运行核心。

不是Framework，而是运行环境。

---

模块：

```text
nebula-runtime/

├── runtime-core
├── runtime-context
├── runtime-lifecycle
├── runtime-event
├── runtime-extension
└── runtime-starter
```

---

## runtime-core

平台 Web 运行基础：统一响应、异常处理、JSON 序列化、扩展点注册。

**REST 暴露约定**：使用 `@RestService` 声明控制器路径与分组；控制器继承 `BaseController`，或采用等效机制（如组合式基类、`@ControllerAdvice` + 接口默认方法）统一提供分页、上下文访问等能力，避免各模块重复样板代码。

---

## runtime-event

统一事件（基于 Spring `ApplicationEvent` 或可选消息总线）：

```
ResourceCreatedEvent
PluginInstalledEvent
RoutePublishedEvent
TaskFinishedEvent
NebulaConfigChangedEvent
```

发布方：各域 Service；订阅方：Governance 审计、Release 状态机、Monitor、`nebula-config` 刷新等。

---

## runtime-context

统一上下文，聚合租户、安全、链路与运行时信息。

# 10. nebula-plugin

## 定位

PF4J 类动态插件平台。

插件不直接绑定 Spring ApplicationContext；通过 adaptor 接入 Boot 生命周期。

---

结构（与仓库对齐）：

```text
nebula-plugin/

├── nebula-plugin-api           # 扩展点 / 描述符 API
├── nebula-plugin-core          # 运行时、管理器、加载器（合并原 runtime/manager/loader）
├── nebula-plugin-repository    # 本地仓库 + 远程仓库 SPI（Maven/HTTP）
├── nebula-plugin-sdk           # 面向插件开发者的门面
├── nebula-plugin-adaptor       # Spring Boot 集成适配（Controller 注册、加载锁等）
├── nebula-plugin-bom           # 插件开发依赖 BOM
└── nebula-plugin-starter
```

能力：

- 在线安装 / 卸载 / 更新
- 生命周期管理（load / start / stop）
- 本地 PF4J 安装可用；远程 Maven 仓库需真实下载实现（见 current-state-analysis B-8）

# 12. nebula-database

## 定位

数据库访问平台。

---

结构（与仓库对齐）：

```text
nebula-database/

├── nebula-database-core          # 含多命名数据源注册；Flyway 迁移约定内聚于此
├── nebula-database-mybatis
├── nebula-database-jpa
├── nebula-database-adapter/      # 方言与元数据 SPI 聚合
│   ├── nebula-database-adapter-core
│   ├── nebula-database-adapter-postgres
│   └── nebula-database-adapter-mysql
└── nebula-database-starter
```

> 不单独拆 `database-migration` / `database-observability` 模块：迁移脚本按应用或子域目录约定放在 core / 各业务域；SQL/连接池监控可内聚于 core 或接入 `camel-monitor` / Actuator。Oracle 等方言按需扩展 adapter。

---

## database-core（数据源）

数据源注册中心，支持多命名数据源与动态注册。读写扩展由高可用数据库集群承担，平台层不提供主从自动路由。

Schema 迁移主路径为 Flyway；按应用或平台子域拆分脚本目录。

---

## database-adapter

数据库方言适配：元数据查询 SPI、方言特定 schema 操作与类型映射。当前 Postgres / MySQL 可用；Oracle 待按需实现。

---

## database-mybatis / database-jpa

MyBatis：Mapper 扫描、SqlSessionFactory 定制；MyBatis-Plus 可按 classpath 检测启用。  
JPA：Entity / Repository 扫描与 Hibernate 配置。  
`database-starter` 支持二者并存。

# 14. nebula-config

## 定位

统一配置加载与刷新框架（**不是**业务配置 CRUD 管理端）。

支持双模式：

| 模式       | 配置                        | 数据来源                             | 场景                     |
| ---------- | --------------------------- | ------------------------------------ | ------------------------ |
| **basic**  | `nebula.config.mode=basic`  | 指定 JDBC 表，启动期注入 Environment | 单体、演示、轻量私有部署 |
| **center** | `nebula.config.mode=center` | Spring Cloud Config Server / Nacos   | 多应用、多环境、集中治理 |

同时保留原有 `ConfigService` CRUD、内存/JDBC 仓库，以及 CORS/CSP 等运行时策略。认证鉴权归 `nebula-security`；敏感值加解密归 `capability-encrypt`。

业务配置管理 REST 由 `nebula-system-config` / `nebula-module-config` 承担，**不得**再宣称「配置中心 REST」。

实现细节与配置示例见 `nebula/docs/config/index.md`。

---

结构（与仓库对齐）：

```text
nebula-config/

├── config-core                  # ConfigSource / Provider / Snapshot / Watcher / 合并与失败策略 SPI
├── config-model                 # 业务配置分组与变更事件模型
├── config-storage               # basic JDBC provider、表映射、CRUD 仓库、文件快照
├── config-center-api            # 配置中心 provider SPI（HTTP、文档解析、轮询 watcher）
├── config-center-spring-cloud   # Spring Cloud Config Server 适配
├── config-center-nacos          # Nacos OpenAPI 适配
├── config-runtime               # 白名单刷新、NebulaConfigChangedEvent、健康检查
├── config-autoconfigure         # EnvironmentPostProcessor + 按 mode 条件装配
└── config-starter               # 应用唯一依赖入口
```

---

## 关键行为

- 启动期通过 `NebulaConfigEnvironmentPostProcessor` 加载；外部属性源位于 env/system 之后、`application.yml` 之前
- 失败策略：`fail-fast` / `use-snapshot` / `ignore`
- 运行期仅刷新 `refreshable-prefixes` 白名单；数据源等 bootstrap 键标记需重启
- 未设置 `nebula.config.mode` 时不启用启动期外部加载（兼容仅用 CRUD 的应用）

# 19. nebula-subscribe

- 为 Console、业务模块与集成域提供一致的订阅 API

## camel-subscribe

Camel 集成域的订阅**实现**，依赖 `nebula-subscribe` 的平台模型与投递能力。

在本模块内完成：

- **Polling**：基于 SQL 的库表轮询与变更事件产出
- **CDC**：变更捕获路由与事件转换
- **集成侧适配**：将 Camel Route 产出的事件注册到平台订阅通道（含 SSE 等）

库表订阅、CDC 等采集与路由逻辑归属本模块；主题管理、订阅者注册与跨域投递归属 `nebula-subscribe`。

# 21. nebula-modules

可插拔的**业务公共模块**，依赖平台能力层，提供领域 REST 与持久化。

```text
nebula-modules/

├── nebula-module-user
├── nebula-module-organization
├── nebula-module-file
├── nebula-module-config              # 业务配置管理 UI/API（非配置中心）
└── nebula-module-tenant-extension
```

技术能力（缓存、日志、消息、WebSocket 等）归属 `nebula-capability`；调度、集群、版本等归属对应平台模块，不在此重复定义。

集成与执行类 API 由 Camel Console / Executor 暴露；通用业务管理 API 由各 module 暴露。

# 28. 模块设计原则

- **单一语义**：每个 Maven 模块只表达一种平台职责
- **依赖向下**：业务模块不反向依赖平台应用
- **能力不泄漏**：integration 仅提供连接，业务 API 在 capability 及以上
- **Resource 统一**：可管理对象均纳入 Resource 模型与治理流程
- **读写约定**：数据访问层区分读/写职责，按命名数据源配置
- **配置职责三分**：`nebula-config`（加载/刷新）≠ `system-config`（系统配置域）≠ `module-config`（业务配置 REST）

# 30. 架构原则

| 议题                         | 原则                                                                                        |
| ---------------------------- | ------------------------------------------------------------------------------------------- |
| Integration vs Capability    | 连接在 integration，业务语义在 capability                                                   |
| Config 三分                  | 加载/刷新在 `nebula-config`；系统配置域在 `system-config`；业务配置 REST 在 `module-config` |
| Config vs Security           | CORS/CSP 等运行时 Web 策略可挂 config-runtime；认证鉴权在 security                          |
| Governance vs Camel Security | 发布审批在 governance，运行时 enforcement 在 camel-security                                 |
| Subscribe vs Camel Subscribe | 平台订阅模型与投递在 subscribe，库表/CDC 采集在 camel-subscribe                             |
| DAG                          | 接口编排归 camel-dag，任务编排归 nebula-task                                                |
| 多数据源                     | 平台提供命名数据源注册，不提供应用层主从路由                                                |
| 租户                         | 平台上下文在 tenant，领域扩展在 camel-tenant / modules；拦截器须真正隔离数据                |
| 管理入口                     | 过渡期 demo-camel-\* 与 platform-console 双轨；目标统一到 platform-\*                       |
| 平台闭环                     | Resource → Governance → Version → Release → **真实 Runtime Deploy**（非仅状态翻转）         |

## 33.2 优先级 backlog（架构视角）

### P0 — 平台闭环与集成可信

1. **真实 Deploy**：`DeployTarget` 对接 Camel Runtime / PluginManager / Task 激活；至少一种 Resource 走通 Draft → Version → Approval → **真实 Deploy** → Runtime
2. **CDC 硬化**：生产配置禁止静默 Simulated fallback；offset 持久化与断连重连；事件格式对齐 `nebula-subscribe`
3. **契约消费**：后端 OpenAPI ↔ Studio `generate:contracts` 被业务代码实际引用（管道已有）

### P1 — 隔离、调度、入口

4. **租户 SQL 隔离**：拦截器注入 `tenant_id`（或等价方案）；持久化租户仓；组织-租户绑定
5. **任务 DAG / 分片接线**：`DependencyGraph`、`TaskShardManager` 接入 Trigger/Scheduler 主路径
6. **统一管理入口**：Studio 默认基址切 `platform-console`；真实健康聚合；过渡期保留 demo 双轨
7. **配置治理收口**：业务文档与调用方不再手工编排加载顺序；刷新白名单持续收敛（双模式框架已完成）

### P2 — 实时、集群、体验

8. **消息 / WebSocket 生产化**：默认 Kafka；WebSocket 集群广播；与 subscribe SSE 统一事件模型
9. **集群发现**：Redis 锁 / K8s 或 Consul 发现；收敛 task 与 cluster 两套分片概念
10. **前端 features**：`route-designer` / `subscription-manager` / `version-diff` 落地或删除假模块；E2E 覆盖登录→租户→订阅→Gateway

### P3 — 扩展

11. 插件远程仓库真实下载与索引
12. OpenTelemetry / Micrometer；monitor 与 observability 模型统一
13. Oracle 等方言按需；integration 与 capability 运维面加深
