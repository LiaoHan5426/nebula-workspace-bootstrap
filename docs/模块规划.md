# Nebula 平台模块规划设计文档

## 1. 项目定位

Nebula 是一个基于 Spring Boot 的企业级应用运行平台。

目标不是重新实现 Spring Framework，而是在 Spring Boot 基础上提供企业应用所需的平台能力：

- 应用运行环境
- 动态插件体系
- 资源治理体系
- 版本管理体系
- 发布部署体系
- 配置管理体系
- 任务调度体系
- 接口集成平台
- 安全认证体系
- 多租户体系

Nebula 的最终目标：

> 形成统一的企业应用运行平台，使业务应用、接口集成、任务调度、插件扩展均基于统一的平台模型运行。

本文档描述**重构后的目标模块结构**与职责边界；迁移步骤见 [第 32 节](#32-迁移步骤)。

# 3. 核心平台模型

Nebula 平台核心由以下部分组成：

```text
                 Resource

                    |

              Governance

                    |

              Version Control

                    |

                Release

                    |

                Runtime

                    |

        Plugin / Camel / Task / App
```

---

## 3.1 Resource

资源模型。

定义：

> 平台中所有可管理对象。

包括：

- Camel Route
- Plugin
- Task
- Config
- DataSource
- API
- Application

统一资源模型：

- 资源标识、类型、归属
- 租户、版本、状态

---

## 3.2 Governance

资源治理。

负责：

- 创建申请
- 修改申请
- 发布申请
- 审核流程
- 操作审计

---

## 3.3 Version Control

版本管理。

负责：

- 快照
- 差异比较
- 历史版本
- 回滚

不负责领域差异。

例如：

Camel Route 如何比较由 Camel 自己实现。

---

## 3.4 Release

发布管理。

负责：

- 发布流程
- 发布状态
- 部署动作
- 回滚

---

## 3.5 Runtime

运行时环境。

负责：

- 生命周期
- 上下文
- 事件
- 扩展加载

---

# 4. nebula-tools

## 定位

纯工具库，仅依赖 JDK / SLF4J 等最小基础库。

提供无状态工具方法；**不包含** Spring 集成、运行时上下文或领域模型。

---

## 结构

单一 Maven 模块，按包组织工具类（字符串、时间、Servlet、对象、BPMN 解析等），**不拆分子模块**。

```text
nebula-tools/    # 单模块 artifact
```

---

# 5. nebula-runtime

## 定位

Nebula运行核心。

不是Framework，而是运行环境。

---

模块：

```text
nebula-runtime/

├── runtime-core
├── runtime-context
├── runtime-lifecycle
├── runtime-event
├── runtime-extension
└── runtime-starter
```

---

## runtime-core

平台 Web 运行基础：统一响应、异常处理、JSON 序列化、扩展点注册。

**REST 暴露约定**：使用 `@RestService` 声明控制器路径与分组；控制器继承 `BaseController`，或采用等效机制（如组合式基类、`@ControllerAdvice` + 接口默认方法）统一提供分页、上下文访问等能力，避免各模块重复样板代码。

---

## runtime-event

统一事件（基于 Spring `ApplicationEvent` 或可选消息总线）：

```
ResourceCreatedEvent
PluginInstalledEvent
RoutePublishedEvent
TaskFinishedEvent
ConfigChangedEvent
```

发布方：各域 Service；订阅方：Governance 审计、Release 状态机、Monitor 等。

---

## runtime-context

统一上下文，聚合租户、安全、链路与运行时信息。

---

## runtime-event

统一事件：

例如：

```
ResourceCreatedEvent

PluginInstalledEvent

RoutePublishedEvent

TaskFinishedEvent

ConfigChangedEvent
```

# 12. nebula-database

## 定位

数据库访问平台。

---

结构：

```text
nebula-database/

├── database-core
├── database-datasource
├── database-mybatis
├── database-jpa
├── database-migration      # Flyway / Liquibase 迁移

```

---

## database-datasource

数据源注册中心，支持多命名数据源与动态注册。读写扩展由高可用数据库集群承担，平台层不提供主从自动路由。

---

## database-migration

数据库 schema 迁移。

支持：

- Flyway（主路径）
- Liquibase（可选）

按应用或平台子域拆分迁移脚本目录。

---

## database-adapter

数据库方言适配。

提供：

- 元数据查询 SPI
- 方言特定 schema 操作与类型映射

子模块：`database-adapter-core`、`database-adapter-postgres` 等。

---

## database-observability

数据库可观测性。

提供：

- 连接池指标
- 执行中 SQL 与慢 SQL 统计
- 监控查询接口

访问控制由 `nebula-security` 与 `nebula-config` 统一策略管理。

---

## database-mybatis

MyBatis深度集成。

支持：

- Mapper扫描
- SqlSessionFactory定制

MyBatis Plus：

通过classpath检测自动启用。

---

## database-jpa

JPA深度集成。

支持：

- Entity扫描
- Repository扫描
- Hibernate配置

---

## database-starter

支持：

MyBatis + JPA同时存在。

# 19. nebula-subscribe

## 定位

平台级事件订阅能力，与具体集成引擎无关。

负责订阅主题定义、订阅者注册、事件投递与通道抽象；各业务域与集成域通过 SPI 或适配器接入，不在此模块实现领域采集逻辑。

---

## 结构

```text
nebula-subscribe/

├── subscribe-core          # 订阅模型、注册表、事件分发
├── subscribe-api           # 订阅/取消、发布接口
├── subscribe-delivery      # 投递通道（SSE、Webhook、消息队列等）
└── subscribe-starter
```

---

## 职责

- 定义平台统一的订阅主题与订阅者模型
- 管理订阅生命周期（创建、续订、取消）
- 将事件投递至已注册通道
- 为 Console、业务模块与集成域提供一致的订阅 API

---

## camel-subscribe

Camel 集成域的订阅**实现**，依赖 `nebula-subscribe` 的平台模型与投递能力。

在本模块内完成：

- **Polling**：基于 SQL 的库表轮询与变更事件产出
- **CDC**：变更捕获路由与事件转换
- **集成侧适配**：将 Camel Route 产出的事件注册到平台订阅通道（含 SSE 等）

库表订阅、CDC 等采集与路由逻辑归属本模块；主题管理、订阅者注册与跨域投递归属 `nebula-subscribe`。

---

## camel-metadata

集成元数据持久化：原子接口、组合接口、连接器、数据源引用等。

---

## camel-security

集成域运行时治理：限流、熔断、白名单、Gateway 策略执行。

发布前审批与策略定义由平台 `nebula-governance` 负责；审批通过后经 `nebula-release` 部署至 Executor。

---

## camel-dag

不是任务Workflow。

---

## camel-plugin

- 数据源插件

Processor类型：

- 前置处理器

- Route节点

# 28. 模块设计原则

- **单一语义**：每个 Maven 模块只表达一种平台职责
- **依赖向下**：业务模块不反向依赖平台应用
- **能力不泄漏**：integration 仅提供连接，业务 API 在 capability 及以上
- **Resource 统一**：可管理对象均纳入 Resource 模型与治理流程
- **读写约定**：数据访问层区分读/写职责，按命名数据源配置

# 29. 建设阶段

## 阶段一 — 平台骨架

建立 `runtime`、`tools`、`database`、`integration`、`capability`、`security` 等基础模块与子模块边界。

## 阶段二 — 平台模型

落地 `resource`、`version-control`、`governance`、`tenant`、`task`、`subscribe`、`cluster`；Camel / Plugin 元数据接入 Resource。

## 阶段三 — 发布与交付

落地 `release`、`config`、`platform` 应用；完善 Camel 订阅、可观测性与集群执行能力。

# 30. 架构原则

| 议题                         | 原则                                                            |
| ---------------------------- | --------------------------------------------------------------- |
| Integration vs Capability    | 连接在 integration，业务语义在 capability                       |
| Config vs Security           | 运行时策略在 config，认证鉴权在 security                        |
| Governance vs Camel Security | 发布审批在 governance，运行时 enforcement 在 camel-security     |
| Subscribe vs Camel Subscribe | 平台订阅模型与投递在 subscribe，库表/CDC 采集在 camel-subscribe |
| DAG                          | 接口编排归 camel-dag，任务编排归 nebula-task                    |
| 多数据源                     | 平台提供命名数据源注册，不提供应用层主从路由                    |
| 租户                         | 平台上下文在 tenant，领域扩展在 camel-tenant / modules          |

## 迁移检查清单

每完成一个域，核对：

1. **依赖方向**：无 integration → module 跳跃依赖；无业务模块依赖 demos
2. **Starter 单一入口**：每个域对外仅暴露一个 `*-starter`（或 BOM）
3. **命名一致**：Maven `artifactId`、Java 根包、`docs` 章节三者对齐
4. **演示可回归**：`demo-camel-console` + `demo-camel-executor`（或 platform-console）启动通过
5. **废弃策略**：旧模块保留至少一个版本周期的 `deprecated` 转发依赖

域间阻塞关系：**B、C 阻塞 D、E**；**F 阻塞 G 的 Resource/Release 闭环**；**H、I 最后收敛**。

## 功能开发检查清单

每批次完成后核对：

1. **AutoConfiguration**：每个域有且仅有一个 `*AutoConfiguration` 注册于 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`
2. **Starter 可启动**：`*-starter` 引入后可独立启动 Spring Boot 应用（无 Bean 缺失或循环依赖）
3. **接口有默认实现**：每个 SPI 至少提供一个内存/默认实现，确保无外部依赖时可运行
4. **测试覆盖**：核心 Service 层单元测试覆盖率 ≥ 70%；AutoConfiguration 有 `@SpringBootTest` 冒烟测试
5. **文档对齐**：Java 根包与 `docs` 章节命名一致
6. **演示可回归**：`demo-camel-console` + `demo-camel-executor` 启动通过
