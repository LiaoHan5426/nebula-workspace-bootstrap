> 最后更新：2026-09-08

> 前端基线：`nebula-studio@406671858aeeffe57cf0320ebfd0d1f6ac4e34fd`
> 本文描述当前 Reactor 与代码边界，不把目标能力写成已实现能力。完成度与风险见 [当前实现状态分析](./nebula-current-state-analysis.md)。

## 1. 项目定位

Nebula 是基于 Spring Boot 的企业应用与集成运行平台；Nebula Studio 是其基于 Module Federation 与 Vite+ 的 Web/Electron 管理与开发体验。平台目标是复用 Spring、Camel、MyBatis、PF4J 等成熟生态，统一资源、治理、版本、发布、插件、任务、租户、安全和集成运行能力，而不是重新实现基础框架。

当前系统可划分为五层：

```text
体验层       Nebula Studio：Web Shell Host、Electron Host、Integration/Settings/Docs/Low-Code Studio Remotes
应用层       platform-console (8090)、platform-integration (8080)、platform-integration-executor (8088)、platform-low-code-write (8092)
领域层       resource、governance、release、version、task、tenant、security、system、low-code
运行层       runtime、camel、plugin、cluster、subscribe
基础设施层   database、integration、capability、config、BOM、tools
```

## 4. 后端模块职责与边界

### 4.1 构建与运行时基础

| 模块 | 当前职责 | 边界 |
| --- | --- | --- |
| `nebula-bom` | Java 与三方依赖版本、插件管理 | 不包含业务实现 |
| `nebula-tools` | 构建/开发工具 | 不参与运行时领域模型 |
| `nebula-runtime` | 生命周期、上下文、事件、扩展点 | 不直接承担资源治理或 Camel 业务 |
| `nebula-cluster` | 节点、发现、锁与集群事件 | 当前仍需分布式接管验收 |

### 4.2 资源治理主链

| 模块 | 当前职责 | 当前限制 |
| --- | --- | --- |
| `nebula-resource` | 资源类型、实例、Registry 和查询 | 各领域 registrar 覆盖仍需扩展 |
| `nebula-governance` | 申请、审批、策略、工作流与审计 | 已有服务/API，真实发布链待闭环 |
| `nebula-version-control` | 快照、版本和 diff | diff 仍需结构化增强 |
| `nebula-release` | 发布、部署、回滚抽象 | 默认 LocalDeployTarget 仅写日志 |

正确调用方向：

```text
Resource Registry
  → Governance Request/Approval
  → Version Snapshot
  → Release
  → Domain DeployTarget
  → Runtime/Executor
```

Release 不能反向承载审批规则，Governance 不能直接操作 Camel Runtime，领域部署由 `DeployTarget` 适配。

### 4.3 插件与 Camel

#### 平台插件

`nebula-plugin` 管理 PF4J 生命周期、descriptor、SDK、安装和仓库。当前真实 Maven 远程下载、搜索、SHA-256 校验与本地索引已实现；剩余重点是签名、可信供应商和依赖约束。

#### Camel 插件与执行

`nebula-camel` 在平台插件之上提供 Camel 领域能力：Connector、Route、DAG、SQL、Trigger、订阅、Gateway、监控和 Console/Executor 装配。平台 descriptor 与 Camel descriptor 不应再次合并为一个大接口。

内置 MySQL、PostgreSQL、HTTP 插件是当前 Reactor 的真实子模块；demo 插件只是 SDK 示例。

### 4.4 数据、集成与通用能力

| 模块 | 职责 |
| --- | --- |
| `nebula-database` | 多数据源、MyBatis/JPA、Flyway、PostgreSQL/MySQL 元数据适配 |
| `nebula-integration` | Redis、S3、Kafka、Mail 客户端与健康检查 |
| `nebula-capability` | 缓存、锁、存储、日志、审计、消息、通知、WebSocket、加密能力 |
| `nebula-config` | basic/center 配置加载、存储、快照、刷新、自动配置 |

`nebula-integration` 是外部客户端适配，`nebula-capability` 是上层可消费的业务无关能力。两者不能仅按三方依赖重复实现同一接口。

### 4.5 身份、租户与系统

| 模块 | 职责 | 当前限制 |
| --- | --- | --- |
| `nebula-security` | JWT、Session、RBAC、Web 安全及可选 OAuth2 子模块 | OAuth2 未进入现行平台装配；MFA/TOTP/恢复未实现；Token 撤销仍为进程内状态 |
| `nebula-tenant` | TenantId、上下文、存储和 starter | SQL 拦截器只检查，不强制注入 |
| `nebula-system` | 应用、组织、用户、用户组织、配置、日志 | 与租户/认证的持久绑定需真实栈验证 |
| `nebula-modules` | 面向平台的文件、用户、组织、配置等组合模块 | 避免与 `nebula-system` 继续重复扩张 |

长期边界建议：

- security 负责认证凭证、会话和授权判断；
- system 负责平台身份实体；
- tenant 负责数据与执行上下文隔离；
- modules 只提供应用层组合，不重新定义领域模型。

### 4.6 任务与订阅

`nebula-task` 已拆分模型、Trigger、Scheduler、Executor、Dependency、Cluster 和 starter；`nebula-subscribe` 负责订阅定义和交付；`nebula-camel-subscribe` 负责 Camel/POLLING/CDC 适配。

剩余边界：

- Task Dependency 必须进入 Scheduler 主路径；
- Task Cluster 必须使用共享节点/锁，而不是仅本地算法；
- 通用 Subscribe 与 Camel Subscribe 共用平台模型，领域模块只维护协议适配；
- CDC 生产模式禁止未授权模拟，并提供共享 offset 与单活接管。

## 6. 前端模块规划（基于 Module Federation 与 Vite+）

### 6.1 应用层（Host 与 Remote）

| 路径 | 类型 | 职责 |
| --- | --- | --- |
| `apps/web` | **Host** | 浏览器 Web 主宿主，集成内置 Login/Workspace 载荷，动态按需加载 Remote |
| `apps/electron` | **Host** | 桌面 Electron 主进程与窗口宿主，管理窗口生命周期、preload 桥接与内置/Remote 视图 |
| `apps/electron-preload` | **Bridge** | capability 驱动的 contextIsolation 安全桥接 |
| `apps/sub-web/integration` | **Remote** | 集成平台 Federation Remote（Portal、Provider、Admin、Camel 业务编排） |
| `apps/sub-web/settings` | **Remote** | 个人、组织与平台设置 Federation Remote |
| `apps/sub-web/docs` | **Remote** | 产品帮助与开发参考 Federation Remote |
| `apps/remotes/low-code-studio` | **Remote** | 低代码工作室与大屏运行态 Remote，导出设计态与运行态组件 |
| `apps/mf-poc-host` | **Sandbox** | Module Federation 概念验证宿主与端到端自动化测试沙箱 |

> 注：原 `sub-web/frontend` 与 `sub-web/login` 已并入 Host 载荷（`@nebula-host-boot/workspace`、`@nebula-host-boot/login`），消除了旧双层 Shell 嵌套与循环重定向风险。

### 6.2 共享分层架构

前端工作区统一遵循分层职责原则（严格禁止反向依赖与循环引用）：

- `packages/contracts/`：领域服务端契约 facade（`auth`、`common`、`generated`、`integration`、`system`），由 OpenAPI 代码生成 + 领域包装，阻断前端硬编码 DTO。
- `packages/platform/`：平台运行时与协议底座：
  - `application-bootstrap` / `startApplication`：显式子应用生命周期装载；
  - `application-contract` / `application-runtime`：应用元数据、能力注入与运行时驱动；
  - `federation-protocol` / `shell-protocol`：跨应用事件、embed 消息契约与 Module Federation 规范；
  - `host-capabilities`：Host 向 Remote 提供的认证、主题、Locale、导航注入能力；
  - `api-client` / `auth` / `state` / `query` / `i18n` / `storage`：请求客户端、认证底座、Pinia 领域状态、Vue Query 缓存与国际化消息工厂。
- `packages/low-code/`：低代码核心能力（`compiler` 编译为 Vue SFC 运行时、`contract` 低代码应用模式契约、`kit` 运行时工具链）。
- `packages/editors/`：按需懒加载的可视化编辑器（`code-editor`、`dag-editor`、`flow-editor`、`integration-panel`、`low-code` 设计器、`low-code-form`）。
- `packages/ui/`：原子组件与视觉系统（`nebula-ui` 基础组件、`shell-ui` 宿主外壳交互、`tokens` 语义化样式变量与 Theme Matrix、`nebula-layout`、`nebula-assembly`、`nebula-agent`）。
- `packages/testing/`：测试基础设施（`msw` 契约 Mock 数据源）。

`configs/` 拆分单一配置源：
- `configs/windows.json`：窗口与 presentation 配置；
- `configs/environments.json`：环境与 API targets 配置；
- `configs/real-stack.json`：真实栈启动配置；
- `configs/e2e.json`：E2E 测试套件配置。

## 7. 依赖规则

### 7.1 后端

1. `*-core` 不依赖 Spring Web 和平台应用。
2. `*-api` 只暴露稳定契约，不泄漏内部存储模型。
3. `*-starter` 负责条件装配，不包含业务流程。
4. `platform-*` 只做组合和运行配置，不复制领域实现。
5. `demos` 不被生产应用依赖。
6. 领域间通过 API/事件/扩展点协作，禁止直接访问对方 Repository。
7. tenant/security/audit 上下文必须跨异步与 Camel 边界传播并清理。

### 7.2 前端

1. 应用可以依赖 core/ui/editors/contracts，反向依赖禁止。
2. 页面只组合 feature 和 ViewModel，不直接散布 fetch/DTO 转换。
3. UI 包不得依赖 Router、业务 API 或应用 Session。
4. shared feature 必须有两个以上消费者、稳定入口和独立测试。
5. 新 API 通过 generated contracts facade，禁止重复手写 DTO。
6. Electron/Web 共用配置与认证语义；差异仅留在 host adapter。

## 8. 当前模块级缺口

| 优先级 | 模块/边界 | 缺口 |
| --- | --- | --- |
| 已完成 G0 | config + 三平台应用 | ConfigService、Context、三应用健康、在线契约和 real-stack 已通过 |
| P0 | release + runtime/camel | 默认 DeployTarget 未驱动真实运行时 |
| P0 | frontend contracts | generated facade 尚未覆盖全部业务消费 |
| P1 | tenant + database | tenant_id 未由统一机制强制 |
| P1 | task + cluster | DAG、唯一调度和故障接管未闭环 |
| P1 | camel subscribe | 共享 offset、单活和接管未生产化 |
| P1 | security + system | MFA/恢复与持久组织/租户认证链缺失 |
| P1 | Studio Integration | app-local feature 需继续收敛，按真实复用提升 |
| P2 | capability message/notification/websocket | DLQ、持久化和跨实例投递不足 |
| P2 | capability storage + integration-s3 | 本地/S3 按 `storageType` 的装配选择仍需专项验证 |
| P2 | camel monitor/observability | 进程内状态需迁移到统一可观测后端 |
| P2 | plugin repository | 签名、可信供应商、依赖约束和企业仓库适配 |

实施顺序和完成定义见 [详细开发计划](./nebula-development-detailed-plan.md)。

## 9. 模块变更准入

新增模块前必须回答：

1. 现有模块为何不能承载该职责？
2. 是否有独立生命周期、稳定 API 或至少两个消费者？
3. 是否会形成与 system/modules、integration/capability、runtime/camel 的重复？
4. 是否同时提供 POM/workspace 声明、测试、README 和运行装配？
5. 是否进入正式 Reactor/manifest？若未进入，必须标注实验或归档状态。

禁止：

- 只创建目录/POM 而无实现；
- 把 demo 作为正式依赖；
- 为满足规划数量创建空 feature；
- 在平台应用复制领域实现；
- 把未来接口写成当前能力。
