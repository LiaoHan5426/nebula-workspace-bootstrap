# Nebula Studio 前端开发记录自动化规划

> 文档版本：v1.0  
> 文档性质：开发记录规划，不承担发布说明或版本变更管理职责  
> 适用范围：`nebula-studio` 前端工作区

## 1. 背景与目标

当前前端缺少一份能够持续回答“这段时间开发了什么”的可读记录。代码、提交和 issue 虽然保留了事实，但分散在 Git 历史、合并请求和任务系统中，人工整理成本高，也不利于回顾阶段性工作。

本方案的目标是：

1. 按时间段自动生成开发记录，例如每日、每周、迭代周期或指定两个 Git ref 之间的记录；
2. 记录开发过程中的功能、重构、修复、测试、文档和工程化工作，而不要求发包或创建版本；
3. 输出面向团队成员和开发者阅读的中文摘要，保留提交、合并请求等可追溯链接；
4. 与发布记录明确分离，避免把未发布、未稳定或仅内部使用的开发内容误当成用户可见变更；
5. 不新增运行时配置文件，不改变现有 `vp`、Vite+ 和 Changesets 的职责边界。

## 2. 开发记录与发布记录的边界

两类记录使用不同的事实来源、生成时机和读者：

| 维度 | 开发记录 | 发布记录 |
| --- | --- | --- |
| 目的 | 回顾一段时间做了什么、为什么做、做到哪一步 | 告知用户某个版本可使用的变更 |
| 触发条件 | 提交、合并请求合入、任务完成、文档更新 | 发布版本、发包、生成 release/tag |
| 范围 | 可包含进行中、实验性、内部重构和测试 | 只包含已确认进入版本的用户可见变更 |
| 时间边界 | 任意两个 ref、自然周、迭代周期 | 一个版本相对于上一个版本 |
| 组织方式 | 按日期/主题/模块/状态聚合 | 按 Added、Changed、Fixed、Breaking 等版本分类 |
| 主要读者 | 开发团队、架构维护者、项目负责人 | 使用者、集成方、运维和发布人员 |
| 是否依赖发包 | 否 | 通常是 |
| 推荐工具 | Git log + 结构化提交 + `git-cliff`/自定义脚本 | Changesets、release 流程和版本标签 |

结论：开发记录不要求开发者手工创建 Changeset。`devlog` 应从 Git 自动生成内存中的 Changeset 风格事实和摘要；Changesets CLI 仅作为未来发布流程的兼容能力，不作为开发记录的人工入口。

## 3. 推荐方案：基于 Git 的开发记录生成器

### 3.1 事实来源

以 Git 为唯一必需数据源，以合并请求元数据作为可选增强数据源：

- 提交标题和正文：功能、修复、重构、测试、文档等分类；
- 作者、提交时间、影响路径和短 SHA：用于追溯；
- 合并请求标题、标签和描述：用于补充用户价值、背景和验证结果；
- 工作区路径：自动推断受影响的 app、package 或领域；
- 可选的 issue/任务号：关联设计决策和待办。

不把代码 diff 直接复制进记录，避免文档膨胀；仅在无法从提交信息判断意图时，引用少量文件路径或摘要。

### 3.2 输出形态

生成 Markdown 文件到根目录 `docs/development-records/`，文件名使用时间范围，例如：

```text
docs/development-records/2026-W34.md
docs/development-records/2026-08-18_2026-08-24.md
```

每份记录建议包含：

```markdown
# Nebula Studio 开发记录：2026-W34

## 本周期摘要

## 按主题归纳
### 功能开发
### 架构与重构
### 缺陷修复
### 测试与质量
### 文档与工程化

## 按模块统计

## 未完成/风险

## 提交与合并请求索引
```

“本周期摘要”和“按主题归纳”是人工可读的核心；“提交与合并请求索引”保证每一条摘要都可以回到事实来源。

### 3.3 分类约定

采用 Conventional Commits 作为推荐格式，但生成器必须兼容历史提交：

```text
feat     功能开发
fix      缺陷修复
refactor 架构或代码重构
perf     性能优化
test     测试
docs     文档
build    构建、依赖和工具链
chore    其他工程维护
```

对于无法识别类型的提交，归入“其他”，不得静默丢弃。提交 scope 用于模块聚合，例如 `studio`、`assembly`、`integration`、`docs`。

## 4. 自动化流程

### 4.1 本地生成

在 `nebula-studio` 增加一个只读 Git 的脚本入口，建议命令如下：

```text
vp run devlog -- --since 2026-08-18 --until 2026-08-24
vp run devlog -- --from origin/main --to HEAD
vp run devlog -- --week current
```

脚本只生成或更新目标 Markdown，不修改源码、版本号、Changesets 文件或 lockfile。默认基线应明确，不能依赖当前分支名称猜测上游分支；未指定范围时可使用最近 7 天，并在输出头部写明实际 ref 和时间范围。

### 4.2 CI 自动生成

建议在以下时机运行：

1. 每次合并到主开发分支：生成当前迭代的增量记录并作为构建产物或 PR 评论；
2. 每周定时任务：生成一份周记录并提交到 `docs/development-records/`；
3. 手动 workflow：允许指定 `from`、`to`、模块和输出文件，便于阶段复盘。

CI 生成应避免机器人提交风暴。推荐先在 CI artifact 中生成，只有周记录或迭代结束时才由维护者确认后提交；若仓库希望完全自动提交，应使用固定机器人分支并在内容无变化时跳过提交。

### 4.3 摘要生成策略

第一阶段使用确定性规则生成，保证离线可用、可重复和可审计：

- 从提交类型、scope、首行标题生成条目；
- 按主题和模块去重、排序；
- 合并 squash 提交时优先使用合并请求标题；
- 将 revert、merge、自动生成提交过滤或单独归档；
- 保留短 SHA 和 PR 链接。

第二阶段可选接入 LLM 做语言润色，但 LLM 只能改写已提取事实，不能自行补充功能、状态或影响范围；原始提交索引必须始终保留。

## 5. 工具选型

### 5.1 首选：`git-cliff` 或等价 Git 日志生成器

`git-cliff` 可以按提交范围生成 Markdown，不依赖版本发布。通过配置模板可实现 Conventional Commits 分类、scope 聚合、链接和时间范围过滤，适合先落地确定性版本。

### 5.2 轻量替代：仓库内 TypeScript 脚本

如果需要读取工作区 package、路径归属、PR 元数据或中文模板，可在现有工具链中增加 `scripts/devlog.ts`，调用 `git log --format` 后自行聚合。该脚本属于开发工具，不应放入产品运行时代码，也不应新增环境配置文件。

### 5.3 不推荐作为主方案的工具

- Changesets：继续服务于包版本、变更集和发布流程；不作为开发记录生成器；
- release-please/semantic-release：围绕 release/tag 设计，会把开发记录和发布语义耦合；
- 仅依赖 issue 手工填写：信息完整但无法覆盖纯重构、测试和文档提交；
- 仅用 `git log` 原样输出：可追溯但不可读，无法形成主题和模块视图。

## 6. 数据质量与提交规范

为了让自动记录具有可读性，提交信息至少应说明“做了什么”，重要改动补充“为什么”和“如何验证”：

```text
feat(assembly): 统一编辑器组件装配入口

- 影响：docs、integration
- 验证：vp run test
```

合并请求模板建议增加：用户/开发者价值、影响模块、验证方式、是否存在未完成项。生成器不得要求每个提交都写长正文；小提交只需清晰首行即可。

## 7. 分阶段实施计划

### P0：可生成

- 确定提交类型、scope 和时间范围规则；
- 选定 `git-cliff` 或实现最小 TypeScript 脚本；
- 增加 `vp run devlog`，生成一份本地 Markdown；
- 添加过滤、去重、短 SHA 和 ref 范围说明；
- 用历史提交验证输出稳定性。

### P1：可持续

- 增加 `docs/development-records/` 目录和周记录 workflow；
- 在 PR 中展示预览，不自动修改发布文件；
- 补充模块归属映射和合并请求链接；
- 对生成器增加单元测试和空范围测试。

### P2：可读性增强

- 增加迭代摘要、未完成项和风险区段；
- 可选接入 LLM 润色，但保留确定性原文和来源索引；
- 允许从开发记录反向链接设计文档、任务和代码评审。

## 8. 验收标准

1. 不创建 Changesets、不改版本号、不发包时，也能按任意时间范围生成记录；
2. 同一 Git ref 范围重复生成结果稳定，且无提交时输出明确的“本周期无变更”；
3. 每条归纳都能追溯到至少一个提交，合并请求链接可用时同时保留；
4. 功能、重构、修复、测试、文档和工程化内容可区分；
5. 记录中明确标注进行中或未完成事项，不把它们写成已发布能力；
6. 发布流程仍由 Changesets/版本标签独立负责，两个目录和两套模板互不覆盖。

## 9. 最终建议

采用“Git 提交为必需来源、合并请求为增强来源、`git-cliff`/TypeScript 规则生成、Markdown 按周期落盘”的开发记录方案。Changesets 继续只处理发布，不为开发记录增加变更集负担。先实现 P0 的确定性生成，再根据团队实际阅读习惯增加 CI 周报和可选摘要润色。

## 10. 中英文双语生成

开发记录可以同时生成中文和英文版本，但不建议直接对最终 Markdown 做全文翻译。推荐增加一个中间层：

```text
Git / PR
  ↓
结构化事实（JSON）
  ↓
中文记录 + English record
```

生成器先提取提交类型、scope、标题、状态、SHA、PR 和链接等结构化事实，再用中文或英文模板渲染。提交、路径、命令、配置键、编号和 URL 等字段保持原样；只有摘要、主题名称和说明进入翻译流程。

建议支持三种模式：`zh`、`en`、`bilingual`。双语模式推荐生成两个文件，便于搜索和站点集成：

```text
docs/development-records/2026-W34.zh-CN.md
docs/development-records/2026-W34.en-US.md
```

两份文件必须共享相同的时间范围、生成器版本和事实来源。应校验中英文条目数量、分类、来源 SHA、链接和代码片段一致；翻译服务不可用时仍生成原语言记录，不能阻塞开发记录流程。

第一阶段可用固定分类和术语词典生成英文模板，第二阶段再接入翻译模型或内部翻译服务。模型只能改写已提取的事实，不得自行补充功能、状态或影响范围；翻译失败的条目标记为待翻译，不得静默删除。

命令可扩展为：

```text
vp run devlog -- --since 2026-08-18 --lang zh
vp run devlog -- --since 2026-08-18 --lang en
vp run devlog -- --since 2026-08-18 --lang bilingual
```

推荐先实现中文确定性生成，再增加英文模板，最后接入可选自动翻译。发布记录仍由独立的发布流程负责，不与开发记录共用文件。

## 11. 全量历史与阶段总结

开发记录不应只覆盖最近一周。生成器支持以下范围：

```text
vp run devlog -- --all --period month --lang bilingual --write
vp run devlog -- --from <old-ref> --to HEAD --lang zh
vp run devlog -- --since 2026-08-23 --until 2026-08-24 --lang zh
```

`--all` 从当前仓库首个根提交开始，生成完整历史，并默认按月拆分；可通过 `--period week|day|none` 改为按周、按日或不拆分。周期记录则继续使用明确的日期或 ref 范围。无范围时仍默认最近 7 天，避免误生成超大的文件。

摘要分两层：

1. 确定性统计：提交总数、功能/修复/重构等分类数量、主要受影响模块和来源索引；
2. 自动 Changeset 风格归纳：按类型和模块聚合 Git 提交，生成“某模块完成 N 项功能/修复/重构”的周期摘要，无需手工写文件；
3. 可选语义总结：未来接入翻译或 LLM 服务，将上述事实改写成自然语言，但必须保留统计和原始提交，不允许模型新增事实。

因此它可以覆盖没有 Changesets 的历史开发，也能提供类似 Changesets 的“按主题归纳”能力；区别是开发记录面向任意时间范围和内部过程，发布记录仍只面向版本变更。真正的 `.changeset/*.md` 文件只在发布流程需要版本决策时生成，不应成为日常开发记录的前置条件。

## 12. 提交规范兼容策略

当前前端仓库尚未全面启用 Conventional Commits：近期提交大多带有 `feat:`、`fix:`、`refactor:` 等前缀，但历史提交存在中英文自然语言标题，且没有 commitlint 强制校验。因此 `devlog` 不能把缺少前缀的提交全部归为 `other`。

生成器采用两级策略：

1. 有 Conventional Commit 前缀时，直接使用其 type/scope；
2. 没有前缀时，根据中英文关键词、变更路径和测试/文档目录推断 `feat`、`fix`、`refactor`、`test`、`docs`、`build` 或 `chore`，并保留原始标题。

后续如需提高新提交质量，可逐步增加 commitlint 或 Git hooks，但不能以此作为历史开发记录生成的前置条件。
